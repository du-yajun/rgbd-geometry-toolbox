## 2026-10-07 · 任务 2：投影 project_points()

### 我亲手写的

- `work/02_project_points.py` 的 `project_points()` 函数体（TODO 1~5 全部完成）
- 手算 A、B 两点，并判断 C、D 的处理方式

### 已验证（实测输出）

- `uv.shape == (4, 2)`、`valid.shape == (4,)`、`valid.dtype == bool`
- 输出：`[[370. 215.] [320. 240.] [nan nan] [nan nan]]`，`valid = [True True False False]`
- 用 `-W error::RuntimeWarning` 运行，无除零警告 —— 说明「先算 valid、再做除法」的顺序是对的
- 手算 A 与代码一致：u = 500*0.2/2.0 + 320 = 370，v = 500*(-0.1)/2.0 + 240 = 215
- 比例检查：(u-cx)/(v-cy) = -2.0，与 X/Y = 0.2/-0.1 = -2.0 一致

### 已能解释

- 投影公式 u = fx*X/Z + cx、v = fy*Y/Z + cy 的由来（相似三角形），以及每个符号的单位
- 为什么必须先判断 `valid = Z > 0` 再做除法（避免除零警告，同时排除光心后方的点）
- 光轴上的点无论远近都投影到主点 —— 这是单目无法从单个像素判断距离的根源

### 反馈中纠正的两点

1. 无效条件不是 `Z == 0`，而是 `Z <= 0`。光心后方的点（Z < 0）同样无效，
   而且它们照公式算出来的像素值在数值上"看起来很正经"，不会报错 —— 更容易悄悄出错。
   另外 z=0 那个平面是过光心、垂直于光轴的平面（光心平面），
   光轴本身是一条线，不存在"光轴平面"这个说法。
2. 问「Z = 0.001 时 u、v 的量级」时答了 1e3，实际是 1e5 量级。
   实测量级（fx=500, X=0.2）：Z=2.0 -> 1e2，Z=0.01 -> 1e4，Z=0.001 -> 1e5。
   量级估算方法是先写 u - cx = fx * X / Z，再把数代进去。
   "非常敏感"的定性结论是对的：Z 变化 1% 时，u 在 Z=0.001 处会移动约 990 像素。

### 遇到并解决的报错

`TypeError: cannot unpack non-iterable NoneType object`（第 106 行）

- 原因：函数算完了 `points_cam` 和 `valid`，但末尾没有 `return`，函数默认返回 None
- 骨架的 TODO 只写到「填数组」，没把 return 单列一步 —— 这是导师出题时的疏漏
- 修复：在函数末尾补 `return points_cam, valid`
- 排查经验：看到 `cannot unpack non-iterable NoneType object`，
  基本可以直接定位为「右边的函数忘了 return」

### 已验证（实测输出）

- `points_cam.shape == (3, 3)`，`valid == [True, True, False]`
- P2 主点还原成 `(0., 0., 2.)` —— X、Y 精确为 0
- 往返一致性误差 `1.665e-16`（浮点精度量级），说明投影与反投影互逆
- 加 `-W error::RuntimeWarning` 运行无任何除零警告
- 半个像素对应的真实距离随深度线性增长：

| 深度 | 半个像素 = 多少米 |
|---|---|
| 0.5 m | 0.0005 m |
| 2.0 m | 0.002 m |
| 5.0 m | 0.005 m |

规律：`dx = 0.5 * Z / fx = Z / 1000`，即误差与深度成正比。

### 学到的一个具体检查习惯

`np.nanmax` 会「忽略」nan，用它检查误差会把失败的点悄悄跳过。
实测对比（2 个点里 1 个无效）：
- 旧写法 `np.nanmax(...)` 打印误差 0.0，看起来完美，实际只算了 1 个点
- 新写法 `assert valid.all()` + 普通 `max()` 直接抛 AssertionError 拦住

结论：**先确认数据有效，再算指标**。这个习惯在阶段 3 处理整图时很关键
（整图里无效像素本来就多，检查逻辑不能也放任 nan）。

1. **ruff 把中日韩宽字符按 2 个宽度计**

2. **`convention = "numpy"` 已自动忽略 D415 和 D413，但不忽略 D400**

   改名成 `work/probe.py` 后立刻报 D103
   —— 我第一次写自检文件用了下划线，差点得出错误结论

4. **命令行 `--select` 会覆盖配置文件里的 ignore**
   实测：配置里 ignore 了 D400，但 `ruff check --select D` 仍报 D400，
   加上 `--ignore D400` 才安静。
   所以验证规范要用 `ruff check .`，不要用 `--select`

出现在 `for d in depth: if d == 0:` 这一行。

- 原因：`depth` 是二维数组，`for d in depth` 每次拿到的是**一整行**（形状 (640,)），
  不是一个像素值。`d == 0` 得到的是布尔数组，而 Python 无法判断
  「一个既有 True 又有 False 的数组」是真是假
- 为什么不该这么写：NumPy 的运算默认作用在整个数组上，
  判无效只需 `depth == 0` 一句，得到同形状的布尔掩码，
  个数用 `.sum()`，比例再除以 `.size`
- 连带发现的三个问题：
  1. `len(depth)` 是行数 480，不是像素数。要用 `.size`（480x640=307200），
     否则比例算错 640 倍，而且不报错
  2. 列表没有 `.min()` 方法，`valid_depth.min()` 会报 AttributeError
  3. `main()` 里读帧写在循环外，5 次打印的是同一帧

### 关于 linter 的认知修正

之前说「ruff 查不出逻辑错误」，不够准确。
这次它报出了 `B007 Loop control variable i not used within loop body`，
恰好精确指出了「读了第 0 帧却用 i 循环」这个 bug。
更准确的说法：linter 查不出逻辑是否正确，但能报出逻辑错误的**症状**。
B007 本身只是可疑，需要人去判断是真 bug 还是无害写法，
如果机械地按提示把 i 改名成 _i，ruff 会满意但 bug 还在。

## 2026-10-10 · 任务 5：整帧反投影生成点云

### 我亲手写的

- `work/05_depth_to_pointcloud.py` 的 `pixel_grid()`：用 meshgrid 生成像素网格
- `depth_to_points()`：整帧反投影，输出 (N, 3) 点和二维有效掩码
- `points_to_colors()`：按同一顺序取颜色并归一化到 0-1
- `main()` 的 TODO 4 到 7

### 踩到的三个坑（全部实测复现过）

1. **`u.flatten()` 没有赋值**。flatten 返回新数组，不修改原数组，
   单独成句等于算完就扔。导致 u、v、z 仍是二维。
   正确写法：`u = u2d.flatten()` 或 `u = u2d.ravel()`。
2. **Y 用了 u 而不是 v**。Y 是竖直方向，必须由行号 v 算。
   实测某像素的 Y 差了 23.0（把 (v-cy) 写成 (u-cy)）。
3. **忘了筛无效像素**。307200 个像素全进了点云，
   多出的 40071 个深度为 0 的点会全部堆在相机原点。

三个坑共同导致输出形状是 (3, 12) 而不是 (9, 3)：
因为三个数组都是二维 (3,4)，column_stack 对二维数组做的是横向拼接。

### 一个关于工具的重要发现

ruff 对这三个 bug **一个都没报**。专门测试确认：

- 孤立的 `1 + 1` -> B018 Found useless expression（报）
- 孤立的 `a.flatten()` -> All checks passed（不报）

推测原因：字面量表达式可静态判定无副作用，而方法调用可能有副作用
（如 a.sort() 是原地排序），工具无法断定它无用，只能放过。
（这是对工具行为的合理解释，不是文档原文，但实测结果如此。）

结论：真正抓到错误的是「打印形状」这个动作，不是 linter。
形状断言是把静默错误转成可见错误的最便宜手段。

### 验证结果

小图（3x4，深度取 11/12/20/21/22/23/30/32/33）：
- points 形状 (9, 3)，valid 形状 (3, 4)，valid 个数 9
- 手算对照：像素 (u=3,v=1,z=23) -> [17.25, -5.75, 23]，与输出一致

真实数据（第 0 帧）：
- points 形状 (267129, 3)，valid 形状 (480, 640)
- **valid.sum() = 267129，与任务 4 独立统计的有效像素数完全一致**（跨任务交叉验证）
- X: -1.366 ~ 1.043 m，Y: -1.171 ~ 0.426 m，Z: 0.955 ~ 2.702 m
- 颜色 (267129, 3) float64，范围 [0, 1]

### 颜色函数的关键点

- 用 `color[valid]` 直接把二维掩码套在三维彩色图上，得到 (N, 3)，
  比骨架提示的「先 reshape 再 flatten」少一个可能搞错的地方
- 归一化用 `/ 255`（不是 `//`，整除会让中间调塌成 0）
- 彩色图不能用 ravel()：`(H,W,3).ravel()` 会把通道也摊平成一维，
  必须用 `reshape(-1, 3)` 保留三通道

### 为什么可以直接逐点相减

两份点云的遍历顺序一致（都按行优先、都跳过无效像素、都没重排序），
所以第 k 个点指向同一物理点，可以直接相减。
用「能追踪顺序」的小图验证过：4 个深度各不相同的像素，
自实现与 Open3D 的输出顺序完全一致，逐点差异 0.0。

反例：若顺序不同（如用 glob 乱序读文件），逐点相减会报出巨大差异，
但点集其实相同，此时必须改用最近邻匹配。
（实测：顺序反转时逐点相减报 0.3，最近邻报 0.0）

### 修正的一处潜在 bug

`(points_ref - points).max()` 只看最大带符号值。若差异恰好全为负，
会返回负数，看起来像「误差极小甚至为负」，掩盖真实差异。
改为 `np.abs(points_ref - points).max()`，并加了点数形状断言。
